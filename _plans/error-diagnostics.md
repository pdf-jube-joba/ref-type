# エラー診断の改善

実装済み（2026-10-04）。
実装と検証の結果は末尾に記録する。

大きな証明のエラーでは、制約の再検査と関連制約の表示がエラー本体の表示よりも重くなる。
診断の生成中にメモリや実行時間を使い切ると、原因の確認ができない。

## 計画時点の簡潔な診断

`REF_TYPE_COMPACT_DIAGNOSTICS=1` を設定すると、型検査エラーに付随する制約診断の生成を省略する。
未解決ゴールでは、関連制約の探索と再検査を省略し、ゴールと文脈を表示する。
最初のエラーが確定した後の独立したモジュールの検査を省略し、そのエラーを返す。
構文エラーがある場合も、型検査を始める前にそのエラーを返す。
エラーの成否とソース位置は通常の診断と共通である。

```sh
REF_TYPE_COMPACT_DIAGNOSTICS=1 target/debug/cli libs/category
```

このモードは、大きな入力でエラー本体を速く確認するための常設機能とする。

## 改善する内容

1. エラー本体とソース位置を先に確定し、詳細な制約診断は必要になったときに生成する。
2. 制約の状態を保存し、診断のためだけに解決済みの制約を型検査し直す処理を減らす。
3. 関連制約の探索、表示件数、式の表示深さと出力サイズに上限を設け、省略した量を示す。
4. 共有された大きな式を何度も展開する表示を避け、名前や共有部分の参照で表示する。
5. 簡潔な診断を CLI のオプションからも選べるようにし、詳細表示への切り替えを明確にする。
6. 診断の生成時間とメモリ使用量を、宣言の検査時間から区別して計測する。
7. 大きな共有式と多数の制約を持つ失敗例で、簡潔な診断の時間と出力サイズを検証する。

## モジュール参照時の再処理

圏論ライブラリの検査では、同じモジュールを参照し直す箇所の後に、標準ライブラリや圏論の同じ宣言の検査ログが繰り返し出た。
簡潔な診断を有効にしても再処理が発生し、時間上限までにエラー本体を取得できない場合があった。
再処理を開始する条件と、通常の具体化に必要な処理なのか、失敗からの復旧による再試行なのかは未確定である。
`src/sema/src/database.rs` の `Database::query` には、失敗後に独立したスコープを新しい `Checker` で検査し直す経路がある。
この経路と観測した再処理との対応、検査済みの依存まで再検査する必要性を調べる。
簡潔なモードで後続検査を省略すると、Kan 拡張の具体化で `module arguments do not allow inference holes` が約27秒で表示された。
後続検査を続けた同じ調査では、50秒と100秒の CPU 上限に達してもエラーが表示されなかった。
これらは最適化した開発用ビルドによる観測値であり、入力を縮約した再現例と比較条件を揃えた計測を追加する。

```sh
REF_TYPE_PROFILE_DECLARATIONS=1 REF_TYPE_COMPACT_DIAGNOSTICS=1 target/debug/cli libs/category
```

1. モジュールの読込、引数の具体化、型検査、失敗後の再試行を区別して計測し、同じ宣言を再検査する呼出経路を特定する。
2. 参照元、具体化した引数、環境の版、キャッシュの命中・失敗を記録し、同じ参照に対する重複処理を確認する。
3. 親モジュール内から子を参照する場合と、検査済みの別モジュールから参照する場合を小さな入力で比較する。
4. 検査済みのモジュールと同じ引数の具体化を再利用できる範囲を調べ、失敗が確定した参照の再試行も整理する。
5. 大きな失敗例で、診断の生成とモジュールの再処理をそれぞれ計測し、終了状態とソース位置を保ったまま重複した検査を減らす。

調査に使った参照の形は次である。
`category` に依存するパッケージでこのモジュールと独立したモジュールを検査し、通常モードと簡潔なモードを比較する。

```text
\import category.Category[] \as Cat;
\import category.Functor[] \as Functors;

\module Reproduction(A, C: Cat.Category, F: Functors.Functor A C) {
  \import category.Kan[].Along[A := A, B := A, C := C,
    K := Functors.identity A, F := F] \as Extension;
}
```

## 検証条件

通常モードと簡潔なモードで終了状態、エラー本体、ソース位置が一致することを確認する。
未解決ゴールの文脈と型を保ち、制約一覧を省略しても原因を追えることを確認する。
通常モードの詳細な制約表示も引き続き検証する。

## 実装結果

2026-10-04 に上記の改善を実装した。

- CLI の `--diagnostics compact` と `--diagnostics detailed` で表示を選べる。
  明示したオプションが環境変数に優先し、`sema::CheckOptions::diagnostics` でも指定できる。
  診断モードは問い合わせのキャッシュキーに含める。
- エラー本体・ゴール・ソース位置を先に保持し、詳細は選ばれたエラーを API の診断に変換するときに生成する。
  保持する solver の snapshot は解を保存し、検査用キャッシュを複製しない。
- 制約の解決状態を検査時に保存し、rollback にも追随する。
  一部のゴールが未解決でも、解決済みの制約を診断のために型検査し直す必要がなくなった。
- 関連制約の探索を 2,048 回・式ノード 32,768 個に、制約表示を一覧ごとに 32 件に、ゴール表示を 64 件に制限する。
  式は深さ 48・512 ノード・4 KiB、文脈は 128 項目・8 KiB、エラー本体は 64 KiB までとする。
  ソース行はエラー位置を含む 240 文字までを表示し、行番号・列番号を保つ。
  件数、部分式数、バイト数で省略量を示す。
- 大きい共有式は `(@expr0 := …)` と `@expr0` の参照で表示する。
- `REF_TYPE_PROFILE_DIAGNOSTICS=1` は診断の保存・ゴール生成・詳細生成・表示・ソース抜粋の時間を計測する。
  メモリの値は各区間の前後のプロセス RSS とその差であり、区間内の全割当量とは区別する。
  宣言の計測時間から診断生成の時間を引く。
- `REF_TYPE_PROFILE_MODULES=1` は読込・参照引数の検査・具体化・失敗後の復旧を記録する。
  参照元、引数の式 ID、環境の版、具体化のキャッシュ命中数と新規作成数を確認できる。

### 再処理の調査と修正

同じ引数の宣言の具体化は、既存の nominal specialization により同じ宣言 ID を再利用する。
名前空間の参照を作る処理と、その宣言の型検査は別の処理である。
親内からの子の参照と、別のモジュールからの参照を比較するテストでは、子の宣言の検査は 1 回だった。

失敗後に別の `Checker` を作り、復旧対象だけで HIR を構成し直す経路では、環境キーが変わって検査済みの依存を再処理していた。
復旧時も要求全体の HIR 配置を保ち、失敗前に保存できた検査済み prefix を問い合わせ内で再利用するようにした。
名前解決そのものが失敗したときは、独立した範囲に縮めて復旧する。
失敗したスコープとその依存元は復旧対象から除き、検証成功した batch だけを永続化する。
`QueryStats::recovery_environment_hits` で復旧用の環境の利用回数を確認できる。
checkpoint の直列化・保持には既存のサイズ上限があるため、再利用は保存できた prefix の範囲になる。

### kernel 登録と復旧の追加調査

区間計測では、詳細モードの約 80 秒のうち約 50 秒が、最後の復旧で実行する `Lowerer::lower_all` の定義登録だった。
同じ入力で、parameter・inductive・datatype の登録は合計 3 ms 未満だった。
定義別では `category.FunctorCategory.Restriction.functor` の登録が約 30 秒を占めた。
`perf` の CPU サンプリングでは、文脈 ID のハッシュ表検索が約 22%、式の属性取得が約 13%、推論キャッシュの検索が約 9% を占めた。

- 検査文脈の ID とメタ変数の有無を接頭辞ごとに保存し、束縛の追加・削除に追随させる。
  開いた項を検査するときに必要な接頭辞だけを計算する。
- 変数・sort・module parameter の推論は直接対応する規則を呼び、変数の型のシフトを型と移動量で共有する。
- 定義登録中だけ使う文脈を登録終了時に破棄し、対応する推論キャッシュも破棄する。
  登録済み定義、solver の保持する項、エラーの項は回収時の生存対象として保つ。
- 復旧では問い合わせ全体の HIR と checkpoint の計画を再利用する。
  名前解決が失敗した場合は、独立した範囲について名前解決をやり直す。

`REF_TYPE_PROFILE_PHASES=1` で、名前解決・checkpoint の保存と復元・kernel 登録・結果収集・workspace の破棄を区別して計測できる。
定義登録の行には定義名も含める。

### 検証

共有を展開すると \(2^{48}\) 個以上の葉になる式と、5,000 件の制約を持つ失敗を作る回帰テストを追加した。
簡潔な診断の生成を 2 秒以内・8 KiB 未満、詳細な制約表示を 32 件以内として検証し、文脈・ゴール・位置の一致も確認する。
制約の解決状態と rollback、モード変更時のキャッシュ、CLI と環境変数の優先順位、長い Unicode ソース行、依存を共有する複数の失敗も検証する。

大きい入力の再現例は `tests/projects/error-diagnostics` に保存した。
このパッケージは上記の Kan 拡張の参照と、それとは独立した失敗するモジュールを含む。

```sh
cargo build -p cli
REF_TYPE_PROFILE_DECLARATIONS=1 REF_TYPE_PROFILE_MODULES=1 REF_TYPE_PROFILE_DIAGNOSTICS=1 REF_TYPE_PROFILE_PHASES=1 \
  /usr/bin/time -f 'elapsed=%e rss_kib=%M exit=%x' \
  target/debug/cli --no-cache --diagnostics compact tests/projects/error-diagnostics
REF_TYPE_PROFILE_DECLARATIONS=1 REF_TYPE_PROFILE_MODULES=1 REF_TYPE_PROFILE_DIAGNOSTICS=1 REF_TYPE_PROFILE_PHASES=1 \
  /usr/bin/time -f 'elapsed=%e rss_kib=%M exit=%x' \
  target/debug/cli --no-cache --diagnostics detailed tests/projects/error-diagnostics
```
