# ref-type Frontend / Semantic Architecture Plan

# 1. 目的

現在の `front` は、source の読み込み、module 構築、macro expansion、名前解決、elaboration、metavariable solving、kernel への lowering までを一つの大きな処理系として担っている。

batch checker としては動作しているが、今後必要になる

* Incremental Check
* Package / Visibility
* semantic query
* metavariable / goal の問い合わせと操作
* 将来の LSP / MCP / proof tooling

の基盤としては、処理段階と状態の lifetime が十分に分離されていない。

今回の目的は、LSP や MCP を実装することではない。

**LSP、MCP、将来の interactive proof tooling が後から薄い adapter として実装できる semantic infrastructure を完成させること**を目的とする。

同様に、package registry や package manager を完成させることも目的ではない。PackageGraph、visibility、identity など、package を処理系に自然に載せるための semantic foundation を整備する。

今回の再設計では、主に次の問題を解消する。

## 1.1 処理段階の混在

現在の frontend representation には、

* source syntax
* macro expansion 前後の syntax
* unresolved / resolved reference
* elaboration 中の expression
* metavariable を含む expression
* checked expression に近い情報

が混在している。

今後は、少なくとも

* syntax
* HIR
* resolved semantic information
* declaration-local elaboration state
* checked kernel representation

を責務として分離する。

ただし、HIR から統一された expression representation 自体を排除することは目的ではない。

HIR の時点では term / type / kind の semantic classification がまだ確定しない場合があるため、`HirExpr` のような unified expression representation を持ってよい。

分離すべきなのは、

> 一つの expression datatype に異なる compilation phase の状態を混在させること

である。

## 1.2 Elaboration state の lifetime

kernel の retained node 数に比べ、現在の frontend/raw processing では非常に多数の temporary node が生成される。

substitution、WHNF、metavariable solving、conversion、implicit inference などの中間結果を project 全体で保持する必要はない。

elaboration state は declaration-local にし、一つの declaration の処理が終われば、

* MetaTerm
* metavariable store
* constraints
* temporary substitutions
* elaboration-local caches

を破棄できる構造にする。

## 1.3 Project semantics と kernel の分離

kernel は trusted calculus の実装に集中させる。

package、module、visibility、user-facing name、source file などは calculus の一部ではない。

これらは semantic layer が所有し、kernel は project structure を知らない状態を目指す。

この kernel boundary の整理だけは、frontend 全体の migration とは別の独立した先行作業として扱う。

## 1.4 Semantic service の確立

今後の tooling が compiler internals を直接操作しないよう、project-wide な semantic information を問い合わせる service を用意する。

これを `sema` とする。

`sema` は LSP server ではない。

`sema` は MCP server でもない。

それらが将来利用できる、

* source state
* HIR
* resolution
* type information
* dependencies
* diagnostics
* references
* goals

などへの semantic API を提供する基盤である。

---

# 2. 最終的に目指す構造

## 2.1 Crate の責務

最終構造では主に、

* `syntax`
* `hir`
* `elab`
* `kernel`
* `sema`

に責務を分ける。

現在存在する `raw` は最終的な独立 architectural layer とはしない。

既存 frontend の elaboration calculus を移行中に隔離するため `raw` crate が存在してもよいが、その最終的な責務は、

* metavariable を含む working term → `elab`
* project/module/dependency information → `sema`
* checked calculus → `kernel`

へ吸収する。

migration 完了時点で、`raw` を恒久的な第6層として残すことを前提にしない。

---

## 2.2 `syntax`

`syntax` は source text に対応する構造を所有する。

主な責務は、

* lexer
* parser
* token
* AST
* span
* source-level identifier

とする。

AST は source representation であり、elaboration の結果を保持しない。

AST に、

* raw term
* kernel term
* resolved definition object
* semantic environment

を埋め込まない。

source location は diagnostics、rename 等の将来の tooling、macro expansion origin のために十分細かく保持する。

---

## 2.3 `hir`

`hir` は source syntax と elaboration の間の semantic syntax を所有する。

主な責務は、

* HIR
* resolved HIR
* `HirId`
* module/item structure
* proof-oriented constructs

とする。

HIR には unified `HirExpr` が存在してよい。

例えば、

```rust
enum HirExpr {
    Name(...),
    App(...),
    Lam(...),
    Pi(...),
    Block(...),
    Enough(...),
    Induction(...),
    ...
}
```

のような構造を許す。

HIR construction の時点で term / type / kind を完全に分類することは要求しない。

例えば、

```text
f x
```

が term-level application なのか type-level application なのかは、elaboration と classifier information がなければ決められない場合がある。

一方で declaration の構造から expected role が分かることは利用する。

例えば、

```rust
struct HirDefinition {
    classifier: HirExpr,
    body: HirExpr,
}
```

とし、

* `classifier` は classifier として elaborate
* `body` はその classifier に対して check

する。

`HirType` のような syntactic category に無理に分割する必要はない。

---

## 2.4 Proof syntax

`\block`、`\enough`、`\induction` など expected type や current goal に依存する syntax は、早期に ordinary expression へ flatten しない。

例えば、

```text
\block {
    \enough A by t;
    ...
}
```

は現在の goal を知らなければ core term に変換できない。

そのため HIR では block/proof structure を保持し、`elab` が expected classifier を持った状態で term を構成する。

原則として、

* context-free な sugar → AST/HIR 段階で desugar してよい
* expected type / goal / metavariable が必要な syntax → `elab` まで保持する

とする。

---

## 2.5 Source state

semantic state の authoritative input は、**現在の source snapshot** とする。

通常の CLI checking では disk 上の source files が source snapshot になる。

editor integration が将来存在する場合は、未保存 editor buffer を含む現在の source snapshot が入力になる。

semantic database、dependency graph、cache、index はすべて source から導出される。

それらを削除しても source から同じ semantic state を再構築できなければならない。

filesystem access は compiler の各 subsystem に分散させず、`FileId` と source abstraction を経由する。

例えば、

```rust
trait SourceDatabase {
    fn text(&self, file: FileId) -> Arc<str>;
}
```

のような interface を持つ。

physical path と semantic identity は分離する。

---

## 2.6 AST から Resolved HIR まで

source processing は責務として次の処理を持つ。

### Parsing

source から AST を構築する。

ここでは ordinary name resolution を行わない。

### HIR construction

AST を semantic processing に適した HIR へ整理する。

module/item outline を取得し、context-free な syntax sugar を必要に応じて除去する。

### Macro processing

macro expansion には完全な ordinary name resolution は不要だが、

* current module
* declaration scope
* 利用可能な macro

を知る必要がある。

したがって macro expansion より先に module/item outline と macro namespace を構築する。

macro hygiene は semantic expression を template に直接埋め込む方式ではなく、`SyntaxContextId` 等の explicit context で表現する。

generated syntax は definition-site information を、captured syntax は call-site information を保持する。

### Ordinary name resolution

macro expansion 後の HIR に対して ordinary resolution を行う。

Resolved HIR の名前参照は semantic item identity を指す。

elaborator は unresolved name を受け取って ModuleGraph を探索しない。

---

## 2.7 Semantic identity

project-level identity は semantic layer が管理する。

必要になる identity として、

* `FileId`
* `PackageId`
* `ModuleId` / `ModuleKey`
* `ItemId` / `ItemKey`
* `HirId`
* `GoalId`

などを想定する。

重要なのは declaration order と identity を分離することである。

module 内 declaration は上から順に environment を拡張してよい。

一方、

```text
DefId = ModuleId + declaration index
```

のように declaration position を semantic identity にはしない。

declaration の挿入だけで unrelated item の identity が変化する構造を避ける。

opaque ID 型自体は crate dependency の都合で `hir` 等の低レベル crate に置いてもよい。

どの source entity を指すかという lifecycle と mapping を `sema` が所有することが重要である。

---

## 2.8 Resolver と Visibility

ordinary name resolution は `elab` から独立させる。

Resolver は、

* local scope
* declaration scope
* module scope
* package scope
* import
* macro syntax context
* visibility

を扱う。

visibility check も Resolver の責務にする。

elaborator の各所で visibility を ad-hoc に判定しない。

基本モデルは、

* item は private が default
* `pub` item は package boundary を越えて利用可能
* constructor / field は owner の effective visibility に従う
* import は明示的に re-export されない限り export しない

程度から始める。

PackageGraph と PackageInterface はこの resolution model の上に置く。

---

## 2.9 Package foundation

今回実装するのは **package system の semantic foundation** である。

registry、remote package distribution、完全な version solver 等を実装することは目的ではない。

`sema` が、

* `PackageId`
* PackageGraph
* package dependency
* package root
* package/module ownership
* package visibility boundary
* exported semantic interface

を表現できる構造を持つ。

Package は namespace そのものとはしない。

概念上、

```text
Package
  └─ Module tree
       └─ Items
```

とする。

module/item identity は package identity の下で一意になる。

kernel は package を一切知らない。

---

## 2.10 Declaration-local `elab`

Resolved HIR の一 declaration を処理するたびに、独立した elaboration session を構築する。

例えば、

```rust
struct ElabSession {
    arena: ElabArena,
    metas: MetaStore,
    constraints: ConstraintStore,
    caches: ElabCaches,
}
```

のような構造とする。

一つの declaration について、

1. Resolved HIR を受け取る。
2. metavariable を含む working term を生成する。
3. constraints / metas を解く。
4. zonk する。
5. kernel representation を構築する。
6. kernel による必要な checking を行う。
7. `sema` が必要とする semantic result を返す。
8. temporary elaboration state を破棄する。

という lifecycle にする。

長期保持しないもの：

* MetaTerm arena
* temporary substitutions
* WHNF intermediates
* metavariable assignment state
* unification state
* declaration-local caches

長期利用できる形に変換するもの：

* checked semantic result
* dependencies
* diagnostics
* goal snapshots
* HIR/source mapping

---

## 2.11 Metavariable と conversion

unsolved metavariable を kernel term に入れない。

そのため `elab` は一時的な working term representation を持つ。

この working representation は現在の `raw::Exp` の一部の後継に相当するが、project-wide persistent representation にはしない。

metavariable が存在する以上、

* occurs check
* meta assignment
* flex-rigid
* flex-flex
* blocked constraint
* zonk

などは elaborator に必要である。

一方、complete term 間の definitional equality を `elab` と `kernel` に二重実装することは避ける。

原則として、

```text
metavariable が関係する equality solving
    → elab

meta-free な complete term の conversion
    → kernel
```

とする。

meta-free subtree を kernel representation に変換して conversion を問い合わせられる interface を整備する。

---

## 2.12 Goal / partial elaboration

unsolved metavariable を単なる失敗として破棄しない。

将来の proof tooling の基盤として、goal を semantic result として問い合わせ可能にする。

例えば、

```rust
struct Goal {
    id: GoalId,
    owner: ItemId,
    span: Span,
    context: Vec<LocalBinding>,
    target: DisplayTerm,
    constraints: Vec<ConstraintInfo>,
}
```

のような情報を提供できるようにする。

`MetaVarId` は declaration-local な実装 ID なので external identity に使用しない。

`GoalId` は semantic/HIR anchor に結びつける。

elaboration result は unresolved goal がある場合にも partial semantic information を返せるようにする。

例えば、

```rust
struct ElabResult {
    term: Option<kernel::Expression>,
    goals: Vec<Goal>,
    diagnostics: Vec<Diagnostic>,
    dependencies: Vec<ItemId>,
}
```

とする。

CLI checker は unresolved goal を failure として扱える。

将来の tooling は同じ情報を interactive state として利用できる。

**今回、goal を操作する LSP UI や MCP tool 自体は実装しない。**

---

## 2.13 Declaration dependency と incremental foundation

incremental checking の最初の単位は declaration とする。

expression-level の fine-grained incremental evaluation を前提にしない。

各 declaration について、

* source/HIR input
* resolved references
* direct item dependencies
* scope dependencies
* elaboration/check state
* diagnostics

を semantic information として取得できるようにする。

definition dependency だけでは name resolution の変更を捉えられないため、

* item add/remove
* rename
* import change
* visibility change
* macro declaration change

など scope structure の変更も invalidation input として扱える設計にする。

最初は conservative invalidation でよい。

---

## 2.14 Fingerprint と checked-state reuse

persistent reuse のため、declaration/module/package の semantic input に fingerprint を定義できる構造を持つ。

fingerprint は単なる file timestamp ではなく、

* relevant source content
* dependency fingerprints
* compiler/language version
* relevant configuration

など、checking result に影響する入力から構成する。

Merkle-style に dependency fingerprint を取り込むことで、source 自身が変わらなくても dependency が変化すれば fingerprint が変わるようにする。

主要な目的は、

> 同一 fingerprint の入力が以前 kernel まで正常に検証されているなら、その checking を再利用できる

こと。

これは必ずしも、

```text
hash -> serialized kernel result
```

という artifact cache を意味しない。

最低限、

```text
fingerprint -> successfully checked
```

という persistent checked-state を保存して、同じ入力について elaboration / kernel checking を省略する方式も許容する。

checked-state reuse と semantic artifact caching は別の最適化として扱う。

temporary `elab` state を persistent cache に保存しない。

persistent state は source から再構築可能でなければならない。

具体的な storage backend は architecture の本質ではない。

Salsa persistence、SQLite、単純な cache files 等は、この semantic model が完成した後に選択できる。

---

## 2.15 `sema` query API

`sema` は mutable compiler pipeline の facade ではなく、source snapshot から semantic informationを問い合わせる service とする。

例えば、

```rust
parse(file)
hir(file)
resolve(item)
elaborate(item)

diagnostics(file)
definition_at(file, position)
references(item)
goals(file)
```

のような query surface を持つ。

すべてを最初から public API として完成させる必要はないが、内部 architecture はこの問い合わせモデルで構成する。

LSP/MCP 固有の protocol object を `sema` に持ち込まない。

---

## 2.16 Diagnostics

semantic boundary では plain `String` を主要な diagnostic representation にしない。

例えば、

```rust
struct Diagnostic {
    code: DiagnosticCode,
    severity: Severity,
    message: String,
    primary: Span,
    secondary: Vec<RelatedDiagnostic>,
    notes: Vec<String>,
}
```

のような structured diagnostics を使用する。

parser、macro processing、resolver、elaboration 等から source location 付き情報を取得できるようにする。

この representation は将来 CLI、LSP、MCP 等が共有できる。

**ただし今回 LSP/MCP への protocol conversion は実装しない。**

---

# 3. 実装計画

今回の作業を多数の Phase に分割しない。

実装単位は二つだけとする。

## 3.1 Kernel isolation

kernel の project-level dependency の除去だけは、frontend/sema migration に先行する独立した変更として完了させる。

対象は主に、

* `ModuleId`
* project-level `DefId`
* `ModuleParamId`

である。

module parameter は kernel では outer local context / bound variable として扱う。

inductive/datatype 等、calculus 上 nominal identity が必要なものには、

```rust
struct InductiveId(u32);
struct DatatypeId(u32);
```

のような kernel-local opaque ID を使用する。

必要なら ordinary global expression の origin を表す kernel-local `GlobalId` を追加してよい。

ただし `GlobalId` は package/module/name を知らない。

対応は semantic layerが所有する。

kernel isolation の完了条件は、

> kernel が source/module/package/visibility/user-facing identity を必要とせず calculus checking を行えること

とする。

---

## 3.2 Frontend / Semantic Infrastructure Migration

kernel isolation の完了後、残りの frontend redesign は**一つの完結した migration として最後まで実装する**。

この migration を、

* HIR を追加した
* declaration-local arena を追加した
* resolver を追加した
* `sema` crate を追加した

といった中間状態で完了扱いしてはならない。

実装内部では依存関係上、任意の順序で変更してよい。

例えば、

1. source abstraction と semantic IDs を導入する。
2. AST/HIR/resolved information を整理する。
3. macro resolution と ordinary resolution を分離する。
4. elaboration state を declaration-local にする。
   5.既存 `raw` の責務を `elab` / `sema` へ移す。
5. Resolver / Visibility / PackageGraph foundation を作る。
6. declaration dependency / fingerprint 情報を作る。
7. goal / diagnostic / semantic query 情報を `sema` から取得可能にする。
8. existing call sites を新 architecture へ移す。
9. obsolete compatibility path を削除する。
10. repository 全体の既存 library/tests を新 architecture で通す。

という順序は考えられる。

しかしこの番号は **milestone でも Phase でもない**。

途中で作業を終了するための区切りではなく、最終状態に到達するための implementation order の例にすぎない。

**この migration は下記 Completion Criteria をすべて満たすまで完了ではない。**

---

# 4. Out of Scope

この architecture migration の目的は将来機能の**基盤整備**である。

以下は今回実装しない。

## LSP server

実装しないもの：

* LSP protocol handling
* editor connection
* hover request handler
* rename request handler
* completion
* go-to-definition protocol integration
* LSP diagnostics transport

ただし、これらを将来実装するために必要な semantic information は `sema` から取得可能な構造を目指す。

## MCP server

実装しないもの：

* MCP server
* MCP protocol handling
* AI-facing MCP tools
* MCP transport

ただし、goal、definition、type、reference 等を将来 MCP から利用できる semantic foundation は整える。

## Proof UI

Agda/Emacs のような interactive UI は実装しない。

metavariable / goal の semantic representation と問い合わせ可能な基盤だけを整える。

## Package distribution

今回の Package work は semantic foundation に限定する。

実装対象外：

* package registry
* publish/download
* remote registry protocol
* 完全な semver solver
* package hosting

PackageGraph、visibility、semantic identity 等の compiler-side foundation は対象とする。

# 5. Completion Criteria

Frontend / Semantic Infrastructure Migration は、以下をすべて満たした場合にのみ完了とする。

## Representation

* AST が elaborated/raw/kernel semantic object を保持していない。
* HIR が source と elaboration の間の persistent semantic syntax として存在する。
* HIR に unified expression representation を持つことは許容する。
* HIR construction 時点で term/type/kind の完全分類を要求しない。
* resolved reference と unresolved source syntax の責務が分離されている。
* metavariable を含む working term が persistent HIR representation と混在していない。

## Elaboration

* metavariable-bearing terms は `elab` 内部の working representation になっている。
* elaboration temporary state は declaration-local である。
* declaration 完了後に temporary arena/cache/metavariable state を破棄できる。
* proof blocks / `\enough` / `\induction` 等の goal-directed syntax は expected type を利用して `elab` が処理する。
* complete term の definitional equality を frontend に丸ごと再実装する構造を避け、可能な範囲で kernel conversion を利用する。

## `raw`

* `raw` を permanent semantic layer として前提にしていない。
* existing `raw` responsibilities が最終的に `elab`、`sema`、`kernel` の適切な ownership に整理されている。
* syntax/HIR が saved raw semantic expressions に依存し続ける compatibility architecture を最終状態としない。

## Semantic service

* source access が共通 source abstraction を経由する。
  -現在の source snapshot が authoritative input である。
* Module/Item identity と declaration order が分離されている。
* ordinary name resolution が elaborator の責務ではない。
* visibility が Resolver / semantic layer で扱われる。
* PackageGraph / package ownership / package visibility boundary を表現できる。
* declaration dependency と scope dependency を取得できる。
* semantic fingerprint / checked-state reuse を実装可能な dependency model が存在する。
* diagnostics が source location を伴う structured information として取得できる。
* unsolved goal / metavariable informationを semantic result として取得できる。

## Kernel boundary

* kernel が package を知らない。
* kernel が source file/path を知らない。
* kernel が visibility を知らない。
* kernel が semantic module structure を知らない。
* project-level identity と kernel-local nominal identity が分離されている。

## Tooling boundary

* LSP 固有の logic が compiler architecture に実装されていない。
* MCP 固有の logic が compiler architecture に実装されていない。
* それらが将来利用できる semantic information は `sema` から取得できる設計になっている。

## Correctness

* existing source library が新 architecture 上で正常に check できる。
  -既存 tests が通る。
* migration 用に追加した compatibility path が最終 implementation の default path として残っていない。
* source/cache を除く隠れた authoritative state を必要としない。
* persistent cache が存在しなくても source から正しい semantic state を再構築できる。

---

# 6. 設計上の Invariants

migration 後も次の条件を維持する。

* Current source snapshot is authoritative.
* Semantic state is derived from source.
* Cache is never authoritative.
* AST represents source syntax, not elaboration results.
* HIR may use a unified expression representation.
* Semantic classification belongs primarily to elaboration, not parsing.
* Project identity and declaration order are distinct concepts.
* Ordinary name resolution is not performed ad hoc by the elaborator.
* Metavariable-bearing terms are confined to declaration-local elaboration state.
* Kernel receives no unsolved metavariables.
* Kernel does not know package/module/source/visibility semantics.
* Kernel-local nominal IDs and semantic item IDs are distinct.
* `raw` is not a permanent architectural layer.
* Package support in this migration means compiler infrastructure, not a package registry.
* LSP/MCP support in this migration means semantic infrastructure only, not implementation of either protocol or server.
* Persistent checked-state/cache can always be discarded and reconstructed from source.

The final architecture should make Incremental Check, Package, Visibility, semantic tooling, and future LSP/MCP/proof tooling natural consumers of the same semantic infrastructure without making any of those consumers part of the compiler core itself.
