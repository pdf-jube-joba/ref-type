# ref-type Frontend / Semantic Architecture Plan

## 1. 目的と設計判断

Incremental Check、Package、Visibility、LSP、MCP、goal 操作を、同じ semantic service の上に構築する。
現在の source と設定から得られる意味を、宣言単位で再計算し、未完成の状態でも問い合わせられる処理系を目指す。

中心となる方針は、source syntax、名前解決、elaboration の作業状態、kernel の検査済み成果物を、それぞれの寿命に合わせて分けることである。
`sema` がそれらを組み合わせ、CLI と対話的な利用者に共通の API を提供する。
既存の checker を動かしながら、一つの宣言が source から問い合わせ結果になる経路を少しずつ移す。
crate 分割は、この経路の入出力と所有権が定まった段階で行う。

特に、次の設計判断を移行の軸にする。

- 宣言ごとの一時状態と、後続の宣言が参照する不変の成果物を分ける。
- 字句的な名前解決と、型推論を必要とする参照の解決を分ける。
- semantic item の同一性、内容の版、kernel 内の nominal identity を分ける。
- 完成した定義の検査結果と、goal やエラーを含む部分的な解析結果を分ける。
- source snapshot と問い合わせ API を早期に作り、小さな LSP 機能でも設計を検証する。

### 現状の実装から出発する

以下はこの計画を見直した時点の実装であり、変更時には対応するコードを確認する。

| 現在の境界 | 実装上の事実 | 移行への含意 |
| --- | --- | --- |
| [surface syntax](../src/front/src/syntax.rs) | `SExp::ResolvedExp` が raw の `Exp` を持ち、`LocalAccess::Resolved` が module を保持する。 | parser の出力と、macro 処理で解決済みになった構文を別の表現にする。 |
| [elaboration](../src/front/src/elaborator.rs) | `GlobalEnvironment` が raw、kernel、module manager、meta store を所有する。 | 問い合わせを独立に再実行できる入力と出力を切り出す。 |
| [宣言の処理](../src/front/src/elaborator/modules.rs) | `MetaStore::clear` は既に複数の宣言境界で呼ばれる一方、lowering は module 群の処理後にもまとめて行われる。 | meta store の局所化に加えて、raw term の保存先と lowering の実行単位を変更する。 |
| [raw 環境](../src/front/src/raw/environment.rs) | 定義の型・本体、module 引数、遅延特殊化、推論・簡約 cache が同じ arena を参照する。 | arena 回収の前に、生存する参照元と成果物への移送を特定する。 |
| [kernel 環境](../src/kernel/src/environment.rs) | 登録検査の一時ノードは既に scope 終了時に回収される。 | front の回収と、長時間の編集による kernel 成果物の回収を別々に設計する。 |
| [goal 診断](../src/front/src/metavariables/diagnostics.rs) | `MetaGoal` と `ConstraintRecord` は構造化されているが、raw handle を含む。 | 既存の情報を、session から独立した表示用 snapshot へ移す。 |
| [module 特殊化](../src/front/src/raw/namespaces.rs) | 元宣言と引数の比較から特殊化の同一性を判断する。 | ID の変更時にも、この同一性を保つ仕組みが必要になる。 |

front/raw の保持ノードが多い原因として、一時ノードの長寿命化は有力な仮説である。
ただし、総割当数、宣言から到達可能なノード数、cache による保持、peak RSS は別々に計測する。
計画上の改善幅は、現在の revision と入力を固定した測定で判断する。

## 2. 責務と依存方向

最終的には次の責務に分ける。
初期実装では `front` 内の module として境界を作り、必要に応じて同名の crate へ切り出す。

| 層 | 入出力と責務 | 状態の寿命 |
| --- | --- | --- |
| `syntax` | source text、token、AST、構文エラー、source range | file revision |
| `hir` | proof 構文を保持する HIR、解決済み参照、source/expansion map | item の解析結果 |
| `elab` | 型推論、metavariable、制約、unification、zonk、kernel 向け構築 | elaboration unit |
| `kernel` | 分類済み calculus、typing、conversion、inductive・reflection の検査 | 所有する検査環境 |
| `sema` | source snapshot、scope、module/package graph、resolver、query、diagnostics、goal、cache 管理 | workspace と各 snapshot |

依存方向は概ね `sema → syntax / hir / elab / kernel`、`elab → hir / kernel` とする。
共有 ID、source location、diagnostic の基本型は、必要なら小さな基盤 module に置く。
`elab` が必要とする定義・member・特殊化の情報は、下位層に定義した interface を通して `sema` が供給する。
この interface 経由の読み取りも依存追跡の対象にする。

kernel は calculus の identity と検査環境を所有し、package・module・visibility の判断は `sema` が所有する。
表示用の binder 名などは意味を持たない metadata として扱える。
`sema` の内部も source、scope/resolution、query orchestration、tooling/index に分け、それぞれの更新条件を明示する。

## 3. 入力、構文、identity

### 3.1 再現可能な入力 snapshot

意味の入力は source text だけでなく、file の存在と配置、module/package の対応、依存 package の内容、言語設定、checker の版を含む。
disk 上の source と未保存 buffer を Source/VFS 層で統合し、問い合わせは一つの不変な `AnalysisSnapshot` を読む。
file の追加・削除・rename や、以前存在しなかった外部 module の出現も入力変更として扱う。

`FileId` は workspace 内の file identity とし、path と text は別の入力にする。
path は外部 module の探索に影響するため、探索結果の依存に含める。
package 導入前も、単一の workspace package と root の対応を入力として用意する。

位置は `FileId`、file revision、UTF-8 byte range の組で表す。
editor の位置表現への変換は adapter で行う。
結果には `RevisionId` を付け、古い位置情報を最新 buffer へ適用するときは版を照合する。

### 3.2 AST と HIR

AST は source の構文を表し、semantic な参照先は lowering 後の HIR に記録する。
式、identifier、binder、hole に range を付ける。
元の text と token/range を保持し、コメントを含む編集対象の範囲を復元できるようにする。
lossless CST の採用は、編集機能に必要な情報量と parser の改修費用から決める。

parser は構文エラーと回復済み AST を返せるようにする。
宣言境界や閉じ括弧を回復点とし、壊れた宣言の後にある独立した宣言についても outline と診断を取得する。
欠けた式は明示的な error node として保持する。

HIR は `\block`、`\enough`、`\induction` など、expected type や current goal を必要とする構造を保持する。
context-free な sugar は HIR 構築時に展開する。
各 HIR node の origin は、直接の source occurrence、macro 展開、生成された projection などを区別する。
macro 展開には呼出位置、定義位置、capture 元、展開の親を記録する。

### 3.3 Identity と内容の版

| 識別子 | 意味と有効範囲 |
| --- | --- |
| `ItemId` / `ModuleId` | workspace 内で item や module を追跡する identity |
| `ItemKey` | package identity、module path、item の種類・名前などから作る再構築用の key |
| `ItemVersion` / fingerprint | 本体、scope、依存成果物などを含む計算内容の版 |
| `HirId` | 一つの item の HIR 内での node identity |
| `GoalId` | revision、owner、goal の局所番号からなる問い合わせ用 identity |
| kernel の nominal ID | 一つの検査環境で inductive/datatype を識別する identity |

宣言順序は scope を決める情報として別に持つ。
通常の名前付き item は親・種類・名前で対応付け、前方に別名の宣言を挿入しても identity を保つ。
重複した宣言や回復構文には局所的な識別情報を付け、対応が曖昧なら新しい ID を割り当てる。
rename や移動を跨ぐ対応は補助情報として扱い、cache の正しさは内容と依存の版で判定する。

`ItemId` が同じでも本体は変更される。
query result や kernel 成果物の再利用には `ItemVersion` と依存成果物の版が必要になる。
process 内の ID の数値と、永続 cache の key は別に扱う。
異なる snapshot の goal を対応付ける情報も保持できるが、操作時には対象 revision で再確認する。

## 4. Macro、名前解決、module

### 4.1 宣言順序を含む処理

概念的な流れは次のとおりとする。

`source → parse/outline → declaration scope → macro expansion → lexical resolution → elaboration → kernel check`

module の outline は先に作り、宣言位置ごとに利用可能な binding と macro の scope を構成する。
展開で得た式や binder は、その展開 context の下で解決する。
処理段階は interface として分けつつ、宣言順序に沿って必要な段階を反復する。

現状の [module scheduler](../src/front/src/elaborator.rs) は、module tree の予約、親への依存、import 依存による順序付けを行う。
module 間の処理順序と、module 内の通常宣言・macro の可視順序を区別して仕様化する。
循環 import は依存経路と source location を持つ診断にする。
前方参照の範囲は既存の挙動を確認した上で固定する。

### 4.2 Hygiene

identifier は名前に加え `SyntaxContextId` を持ち、定義側の scope と宣言位置、呼出側の capture、生成 binder を区別する。
macro template の自由名は定義位置の scope で解決し、capture した構文は呼出側の context を保つ。
入れ子の展開と再帰展開でも、この context と expansion origin を引き継ぐ。

現在の `prepare_template` は、module parameter を `SExp::ResolvedExp` に置き換えることがある。
移行後は semantic parameter reference と、module instance の代入を表す情報で保持する。
単なる名前と definition-site の印だけでなく、特殊化された module から使う macro の意味も再現する。

### 4.3 Lexical resolution と型依存の解決

local binding、明示的な module path、通常の item 参照は Resolver が解決する。
Resolved HIR には `LocalId`、`ItemId`、module instance reference などを記録する。

一方、`#first{pair}` のようなフィールド参照は、receiver の型から owner を決める必要がある。
現在も `GlobalEnvironment::field_projection` が型を推論して record を取得している。
HIR には receiver、member 名、利用位置の access context を残し、型が判明した時点で Resolver の member lookup interface を呼ぶ。
未解決 meta によって型が定まらない場合は、制約として保留する。

visibility 判定は Resolver に集約し、型依存の lookup も同じ判定を通す。
elaboration が選んだ参照先を occurrence map に記録し、definition/reference query と依存追跡に反映する。

### 4.4 Module instance と nominal identity

module は引数付きの名前空間であり、instance は元 module、合成された引数、元宣言への対応を持つ。
名前の探索と、引数の elaboration・検査・特殊化を分け、後者は型情報を得ながら実行する。

現行仕様では、同じ元宣言に同等な引数を渡した instance は同じ nominal type を共有する。
この同等性には引数の構文上の一致だけでなく、既存の conversion・reflection による比較が関わる。
異なる元宣言、異なる引数、未使用の引数や証明引数の扱いも、既存の同一性判定に従う。
詳細は [特殊化の実装](../src/front/src/raw/namespaces.rs) と [substitution identity の例](../tests/ok/modules/substitution-identity.ref) を基準にする。

`InstanceKey` の候補は元宣言と引数種別など、意味的に同等な引数を同じ集合に保てる情報で絞る。
引数の構文 hash が異なる場合も必要な conversion を行い、共有を確定する。
外側からの代入、nested import、Program datatype と Set reflection の対応を同じ規則で扱う。
instance の型検査・比較で読んだ定義も依存に含める。

元宣言の一般性は元の parameter context で検査する。
利用された instance は必要時に特殊化して検査する。
datatype、mirror、constructor、生成 projection は一つの公開単位として扱う。

### 4.5 Visibility と Package の契約

visibility は language change として、resolver 抽出とは区別して導入する。
まず現行のライブラリが利用している可視性を再現し、export/import の参照関係を取得する。
その後、default private、package 内公開、package 外公開、re-export の規則を決め、必要なライブラリ修正と一緒に移行する。

初期案は private を宣言 module と子孫で利用可能とし、`pub` を package 外にも公開する形とする。
package 内公開の必要性は、既存 library の import を使って判断する。
constructor/field は初期には owner の可視性を継承し、import alias は明示したものを re-export する。

公開項の signature に現れる型・module の可視性と、macro の definition-site から参照する非公開 helper の扱いを仕様化する。
透明な定義の conversion で必要な本体は、source 上の access 権限とは別に検査環境へ供給する。
この区別により、visibility と定義の透明性をそれぞれ維持する。

## 5. Elaboration の寿命と成果物

### 5.1 Elaboration unit

通常の definition は一つの elaboration unit とする。
inductive と constructor、record と生成 projection、Program datatype と mirror は、整合性を保つ一つの公開単位にまとめる。
module parameter telescope、import 引数、source 上の check/eval query も、それぞれ作業状態の寿命を定める。
将来の相互再帰は、対応する宣言群を unit にする。

`ElabSession` は unit ごとの arena、meta store、制約、局所文脈、推論・簡約 cache を所有する。
既存の定義や datatype は、不変の成果物を参照する interface から読む。
成功・失敗・取消のいずれでも、unit 終了時に作業状態を解放できるようにする。

### 5.2 Raw の保存先を先に作る

現在の raw 表現は、後続宣言の elaboration、conversion、module 特殊化、macro、評価に使われる。
そのため、session を捨てる前に、それらが読む不変の表現が必要になる。

移行時には、meta-free な型・本体・context・特殊化情報を `FrozenDecl` のような所有権付き成果物へ移す。
局所 arena から成果物へ移送するときは handle を付け替え、共有部分木を保つ。
参照済みの定義は ID または共有成果物への参照として保持し、展開に必要な部分の移送量と共有率を測る。
当初は保存用 raw と kernel の二つの成果物を保持し、kernel 項を直接読める elaboration interface の導入後に保存用 raw の必要性を再評価する。

arena 分割の対象は、定義の型・本体だけでなく、module 引数、遅延特殊化、macro capture、context interner、cache の key/value、diagnostic の参照まで調べる。
meta を含む項は局所作業領域に置き、未解決項の表示情報は専用の snapshot へ変換する。
session の終了後に残る成果物は、それ自身または依存成果物が所有する領域だけを参照する。

### 5.3 完成・未完成・失敗の結果

elaboration の結果は、たとえば次のように検査状態を明示する。

```rust
enum CheckStatus {
    Checked(CheckedArtifact),
    Incomplete,
    Failed,
    Blocked { dependencies: Vec<ItemId> },
}

struct ElabResult {
    status: CheckStatus,
    goals: Vec<GoalSnapshot>,
    diagnostics: Vec<Diagnostic>,
    dependencies: DependencySet,
    source_info: SourceInfoMap,
}
```

`CheckedArtifact` は zonk、分類済み構文への変換、kernel の検査を通過した成果物を所有する。
未解決 goal やエラーを含む宣言は、outline や一部の型情報を tooling に返す。
その宣言の検査済み成果物を必要とする後続宣言は `Blocked` とし、独立した宣言の解析は続ける。
未完成宣言の型だけを仮定して進める機能は、条件付き結果の伝播規則を定めた段階で追加する。

名前と宣言位置は outline に保持し、失敗した宣言への参照もその宣言に結び付ける。
これにより、失敗した宣言が外側の同名宣言を隠す場合も、意図した参照先と blocked の原因を保持する。
kernel 登録と検査済み成果物の公開は、unit の検査成功時に commit する。
一部の projection や mirror の失敗、elaboration の別解釈の試行、取消でも、公開状態が中途半端にならない transaction boundary を作る。
取消や資源上限到達は通常の型エラーと区別し、再試行可能な query outcome として扱う。

### 5.4 Conversion と制約解決

meta assignment、occurs check、scope check、flex-rigid/flex-flex、blocked constraint の再開は `elab` が担当する。
meta-free な項の definitional equality は、適切に分類して kernel conversion を利用する方向へ寄せる。

ただし、meta-free でも項が開いている場合は局所 context と、sort・level・family の情報が必要になる。
kernel に渡す rigid subtree の変換を、文脈込みで再利用できるようにする。
meta を含む項の簡約は elaboration 側に残り、反映や注釈を含む簡約規則の整合性を確認する。

現在の elaboration は `erased_convertible`、`can_weaken_to`、`common_ambient_carrier` も使う。
これらの関係と kernel の definitional equality は、用途と成立条件を分けて整理する。
bridge の検証では Set/Prop、Program の型適用、refinement、reflection、open term を含む対応例を比較する。
bridge の変換費用も計測し、局所化後に共有できる処理から順に統合する。

## 6. Kernel の境界

### 6.1 Project identity から calculus identity へ

現在の [kernel ID](../src/kernel/src/ids.rs) は module と宣言 index を含み、raw 側もこれを再公開している。
まず semantic ID と kernel 内の ID の型を分け、対応表を bridge へ移す。
`MetaVarId` の定義は elaboration 側へ置く。

通常の定義は現在も式中の `DefId` 参照ではなく、型注釈付きの本体として表される。
`Annotated` の classifier は typing に必要であり、conversion に対する透過性も維持する。
登録キーを opaque な ID にする変更と、term の意味の変更を分けて進める。

inductive/datatype は kernel-local な nominal ID で参照する。
予約された ID を使って spec を構築し、検査の間だけ自己参照を可能にして、成功後に公開する。
Program datatype と mirror の対応も同じ transaction で検査・登録する。
instance にどの nominal ID を割り当てるかは、4.4 の規則に従って semantic layer が管理する。

### 6.2 Module parameter を context に移す際の条件

module parameter は calculus 上の局所 context として検査する方向へ移す。
ただし module は namespace であり、parameter 全体を product/lambda に包む変換とは区別する。
[既存の例](../tests/ok/modules/substitution-identity.ref) には、証明 parameter を持つ module 内の Set 型定義があり、module の関数化によって追加の product rule を要求すると意味が変わる。

kernel は context 付きの開いた宣言 template を検査し、front/bridge が body と classifier に引数を同時代入する。
inductive の ambient context と datatype 自身の parameter telescope も区別して設計する。
移行対象には次を含める。

- Set/Prop と Program のそれぞれの binder index と、依存する module parameter。
- Program parameter の Set reflection と、反映された context への対応。
- nested module と、呼出側の local binder を含む instance。
- Box の閉性判定と、注釈・定義本体を辿る閉性検査。
- 元宣言、特殊化された宣言、datatype mirror の検査。

この部分は nominal ID の置換とは独立した実装段階にし、小さな template から検証する。

### 6.3 Source occurrence と origin

definition/reference の情報源は、Resolver と elaboration が記録する `HirId → SemanticRef` の occurrence map とする。
同じ kernel node を二つの定義や source occurrence が共有できるため、kernel node から source への対応は多対多になる。

kernel の pretty-printing で元の名前を使う場合は、まず semantic layer の side table を利用する。
term 内の origin marker が必要になった場合は、用途と interning への影響を計測して導入する。
opaque marker を用いる場合も、typing/conversion の意味と source occurrence の記録はそれぞれの層で維持する。

### 6.4 検査環境と成果物の寿命

kernel handle は作成元の arena と環境に属する。
`CheckedArtifact` は所有環境の識別情報と、依存する成果物の版を持つ。
同じ `ItemId` の編集後の定義は、新しい内容として検査する。
古い snapshot を参照している要求がある間は、古い成果物と環境を保持する。

最初の実装では snapshot ごとに kernel 環境を作り直し、再利用する meta-free な宣言成果物を依存順に移送して再検査してよい。
この段階では elaboration の再利用と kernel 再検査の費用を別々に報告する。
その後、immutable な宣言単位の保存領域と依存閉包を使い、検査済み成果物の共有を拡大する。

handle や nominal ID を環境間で移すには、依存先と mirror を含む明示的な再割当てが必要になる。
query cache、古い snapshot、検査環境それぞれに回収方針を設ける。
同じ箇所の編集を繰り返す計測で、使用中の成果物と設定した cache 上限に応じてメモリが安定することを確認する。

## 7. Query と incremental computation

### 7.1 Snapshot 上の問い合わせ

`AnalysisHost` は入力の更新と処理の調停を担当し、`AnalysisSnapshot` は特定 revision の問い合わせを提供する。
API の概形は次のようにする。

```text
snapshot.parse(file)
snapshot.outline(module)
snapshot.scope_before(item)
snapshot.expand(item)
snapshot.resolve(item)
snapshot.check(item)
snapshot.diagnostics(file)
snapshot.type_at(file, position)
snapshot.definition_at(file, position)
snapshot.references(item)
snapshot.goals(file)
```

解析結果は明示された入力と依存結果から決まり、問い合わせ順序によらず同じ意味になる。
宣言の公開、instance の materialization、kernel 登録は不変な成果物と管理された transaction を通して行う。
query の再実行や取消のたびに、共有 mutable environment へ二重登録される構造を改める。

初期実装は一つの解析 worker が kernel 環境を所有する形でよい。
現状の arena や環境には `Rc`・`RefCell` があり、並列化には所有権の変更が必要になる。
まず snapshot の版管理と取消を成立させ、並列解析は成果物の共有方式を決めてから追加する。
長い簡約・制約解決にも取消確認を設け、終了時に transaction を破棄する。

### 7.2 Invalidation の単位

file の再 parse と宣言単位の semantic 再計算から始める。
変更した宣言以降の scope と、その scope を読む宣言を保守的に無効化する。
import や module 構造の変更は、importer、子 module、関連 instance にも伝播させる。

| 変更または読み取り | 追跡する依存 |
| --- | --- |
| 定義の本体・型の変更 | 本体または型を参照・展開した成果物と、それらを利用する後続成果物 |
| 宣言の追加・削除・rename、順序変更 | 宣言位置の scope、member table、影響を受ける import |
| 名前が見つからなかった lookup | 探索した scope の版 |
| macro 定義・利用・順序の変更 | macro scope、definition-site の参照、展開を使用する宣言 |
| module 引数・元宣言の変更 | 特殊化結果、引数の同等性比較、nominal identity の選択 |
| 外部 module の追加・削除・移動 | file の存在、path 解決、module graph |
| visibility・package 設定の変更 | access 判定、export、package graph |
| source range だけの変更 | source map、位置付き診断、goal・reference の位置 |

透明な定義では、signature が同じでも本体変更が conversion や instance の同一性に影響する。
当初の dependency fingerprint は必要な本体も含める。
signature のみへの依存を区別する最適化は、実際の読み取りを追跡できる段階で導入する。

依存関係は最終的な kernel term の参照だけから復元するのではなく、解析中の読み取りから収集する。
型依存の member lookup、meta solving、macro 展開、失敗した探索も対象にする。
初期には scope 全体への依存で扱い、細かい negative dependency は再計算量を見て導入する。

### 7.3 Query engine の選択

まず snapshot、成果物、依存、invalidation の契約を作り、小規模な変更列で動作させる。
Salsa は候補とし、採用前に一つの module で ID の対応、diagnostics、取消、成果物の所有権を試作する。
Salsa は入力からの決定的な計算を前提とするため、既存の登録処理を query へ移す際の設計基準にする。
参考：[Salsa overview](https://salsa-rs.github.io/salsa/overview.html)。

採用判断では、cold check、無変更時の query、局所編集、scope 変更の処理時間と保持メモリを比較する。
永続 cache の方式は query engine の選定とは別に決める。

### 7.4 正しさの基準

各編集後の incremental result を、同じ入力 snapshot から新規に解析した cold result と比較する。
比較対象は宣言の検査状態、型、診断、goal、参照先、instance の同一性関係とする。
process 内 ID や arena handle は正規化して比較する。

編集列には、本体変更、宣言挿入、削除、rename、shadowing、import/macro の変更、未完成な式、error の修復を含める。
同じ query を異なる順序で呼ぶ場合と、途中で取消した後の再実行も比較する。
再利用数の計測と併せて、正しさと incremental 化の効果を確認する。

## 8. Goal と tooling API

### 8.1 Session から独立した goal

`GoalSnapshot` は revision、owner、source/expansion origin、表示用の局所 context・target・制約を持つ。
表示用 term は snapshot が所有する不変の構造にし、未解決箇所は snapshot 内の symbolic hole として表す。
解決のための mutable meta store と、表示用の未解決項を分ける。
target がまだ分からない場合も、その状態を明示する。

`_` の推論不足、`?` の goal、`?N` による共有 goal、内部で生成した meta は区別する。
一つの goal に複数の source occurrence がある場合はすべて保持する。
解析済みの部分項では、未解決 goal の有無に加えて型・局所 context を取得できるようにする。

### 8.2 Goal 操作は source edit を返す

最初の操作は goal の表示と、`give` / `refine` の試行とする。
操作は revision と `GoalId` を受け取り、owner の session を再構築して候補を検査する。
結果は候補の source edit、必要な import、変更後の診断・残る goal として返す。

編集は対象 file の版を付けた提案として返し、適用後の source snapshot を改めて解析する。
古い goal に対する要求には stale result を返す。
複数 occurrence を持つ named goal は、その対応を使って編集範囲を決める。
macro で生成された goal は、call-site の capture など編集可能な source への対応を確認してから提案する。

初期には再 elaboration によって状態を復元する。
応答時間が問題になる場合は、revision に紐付けた session cache を上限付きで導入する。
`apply`、case split、normalize は同じ API 契約の上に追加する。

### 8.3 Diagnostics と protocol adapter

diagnostic は code、severity、message、primary/secondary location、notes を持つ。
parser、macro、resolver、elaboration、kernel bridge の診断をこの形式へ集める。
kernel のエラーは bridge が source occurrence に対応付け、特定できない場合は宣言位置を使う。

LSP と MCP は同じ `sema` API を使う consumer とする。
adapter は文書の版・位置表現、request の取消、通知、edit の受け渡しを担当する。
古い revision の診断を最新文書の診断として公開することを防ぐ。

最初の LSP は diagnostics と definition/hover 程度を対象にする。
references は現在解析済みの範囲と workspace 全体を区別し、結果に index の範囲と完了状態を付ける。
CLI は workspace の検査結果を集約し、未解決 goal・失敗・blocked を検査失敗として返す。
MCP の問い合わせと編集提案も、同じ revision と goal の検証を通す。

## 9. Package と永続化

### 9.1 Package

初期の単一 package モデルを、package root、依存 package、export、内容 fingerprint を持つ `PackageGraph` へ拡張する。
依存の解決結果は manifest と lock 情報などの明示的な入力にし、解析はその snapshot を読む。
package manager による取得・更新と、semantic query による解析を別の操作にする。

package identity は表示名やローカル path から区別する。
依存 package の版・内容の変更は item key、scope、artifact の依存へ伝播する。
まずローカルの複数 package で identity と visibility を検証し、その上に配布・取得を追加する。

### 9.2 永続 cache

永続 cache は入力から再構築できる派生データとする。
まず計測で費用の大きい declaration artifact を対象にし、保存・読込・再検査の合計時間と容量を比べる。
cache key は checker と言語・形式の版、入力内容、package/configuration、scope/macro、推移的な依存成果物の fingerprint を含む。

保存形式では arena handle や process 内 ID を、artifact 内の参照と依存 artifact の参照へ変換する。
読み込み時は現環境の ID へ再割当てし、nominal type と mirror の対応を復元する。
disk 上の「検査済み」という印は検査成功の根拠にせず、復元した宣言を kernel で再検査する。
再検査を省略する方式を検討する場合は、cache の真正性と trusted boundary を別途定義する。

欠損、破損、版の不一致、依存の不一致は cache miss として処理する。
書き込みは一時ファイルからの置換などで完了単位を保証し、容量上限と回収方法を持つ。
persistent symbol/reference index には、入力 fingerprint と解析済み範囲を保存する。

保存形式と store は実測後に選び、SQLite は横断検索や index 更新に適するかを評価する。
query engine に永続化機能を求める場合は、採用版の API、ID の復元、互換性、破損時の扱いを試作で確認する。

## 10. 移行順序と完了条件

各 phase は、既存 checker の挙動を確認できる単位に分けて進める。
architecture の移行と、visibility などの言語仕様変更は、それぞれの完了条件を持つ。

### Phase 0: 現状の意味とコストを記録する

既存の workspace test と library check を基準にする。
module の処理順、macro hygiene、instance の同一性、reflection、goal の分類について、対応する既存テストを整理する。

```sh
cargo test --workspace --locked --offline
cargo build --release --locked --offline
env -u RUST_LOG /usr/bin/time -f 'elapsed=%e user=%U sys=%S maxrss_kb=%M' target/release/cli lib/root.ref --stats
```

build 時間を除き、同じ環境で複数回計測する。
`REF_TYPE_PROFILE_DECLARATIONS`、`REF_TYPE_PROFILE_LOCAL_DEFINITIONS` と既存の `--stats` を使い、必要な到達可能ノード数・unit ごとの計測を補う。
CPU の分析には `/usr/lib/linux-tools/6.8.0-139-generic/perf` を利用する。

完了条件は、revision・入力・実行条件付きの baseline と、raw の長期生存 root の一覧が得られることとする。
単一の巨大宣言の peak と、宣言を跨いだ蓄積を区別する。

### Phase 1: Source snapshot と最小の問い合わせ経路

`SourceDatabase` / VFS、`FileId`、revision 付き location、structured diagnostic を導入する。
既存の batch checker を `sema` の入口から呼べるようにし、当初は snapshot ごとに全体を解析する。
parser の recovery と式・identifier の range を、小さな構文範囲から追加する。
item の対応付け規則も、この段階で導入する。

完了条件は、同じ入力に対する CLI と query の検査結果が一致し、未保存 buffer と構文エラー後の宣言を扱えることとする。
初期の diagnostics adapter を動かし、位置と revision の扱いを確認する。

### Phase 2: 宣言成果物と局所 session

raw の長期生存 root を整理し、保存用の不変成果物と作業領域を分ける。
まず通常の definition 一つで、elaboration、成果物への移送、kernel check、session 解放の経路を作る。
次に module parameter/import、inductive/record、Program/mirror、macro、check/eval へ広げる。
`GoalSnapshot` の切り出しと、検査成功時の commit もこの経路に含める。

完了条件は、session 解放後に後続宣言・診断・goal・特殊化が正しく動き、失敗や取消でも公開状態を保てることとする。
保持ノード数と peak RSS、再コピーと再検査の時間を baseline と比較する。
この測定から、次に kernel 項の直接参照へ進むか、raw 成果物の共有を改善するかを決める。

### Phase 3: HIR、Macro、Resolver の境界

AST と展開後の構文を分け、proof HIR、syntax context、origin map を導入する。
lexical resolution を抽出し、型依存の member lookup と module instance の検査には明示的な interface を設ける。
scope の版と query dependency を記録する。

完了条件は、macro hygiene と module 特殊化の既存挙動が保たれ、通常参照と型依存参照の definition query が得られることとする。
hover/definition と goal 表示を小さな LSP adapter から使い、error recovery 時も確認する。

### Phase 4: Kernel bridge と環境の所有権

semantic ID と kernel ID を分け、検査環境と成果物の所有関係を明示する。
まず opaque な登録キーと nominal ID、次に context 付き module template、reflection・閉性の順で移す。
snapshot 間で成果物を移す経路と、古い環境の回収を作る。

完了条件は、kernel の public API が calculus の情報だけで検査でき、module substitution と nominal identity の意味が保たれることとする。
snapshot を破棄した後のメモリ回収と、異なる環境の handle の取り違えへの検査を行う。

### Phase 5: 宣言単位の incremental query

明示した依存関係に従う invalidation と cache を導入する。
query engine の小規模試作から採用方式を決める。
当初は scope 変更時の過剰な再計算を許容し、elaboration の再利用と kernel の再検査を別に計測する。

完了条件は、7.4 の編集列で incremental result と cold result が一致することとする。
無変更時と無関係な宣言の編集で再利用が起き、反復編集時のメモリが安定することも確認する。
cache を無効にした実行を比較用の経路として維持する。

### Phase 6: Goal 操作と tooling の拡張

revision 付き goal API、session の再構築、編集候補の検査を実装する。
`give` / `refine` から始め、`apply`、case split、normalize と references/index を順に追加する。
LSP に加え MCP を同じ API へ接続する。

完了条件は、提案した編集を適用して再解析すると確認済みの結果になり、古い版への操作を検出できることとする。
macro 由来の goal と named goal の複数 occurrence も確認する。

### Phase 7: 複数 Package と Visibility

単一 package の入力を複数 package に拡張し、4.5 の access/export 規則を確定する。
既存 library の公開宣言を移行し、依存 package の差し替え・export 変更を query dependency に接続する。

完了条件は、同名の module/type を持つ別 package の区別、re-export、公開 signature、macro helper の扱いが一貫することとする。
CLI と対話的な query で同じ判定を得る。

### Phase 8: 永続 cache

測定から保存対象を選び、artifact の serialization、ID の再割当て、kernel 再検査を実装する。
symbol/reference index の保存は用途と更新費用に応じて追加する。

完了条件は、cache の有無、process の再起動、破損・版変更後で検査結果が一致し、保存・読込・再検査込みで対象 workload の時間が改善することとする。

## 11. 維持する条件

- 解析結果は、source・file 配置・package・設定を含む明示的な入力 snapshot から再構築できる。
- 保存される handle は、所有領域と環境の寿命に結び付いている。
- mutable な meta state は elaboration unit に属し、goal は独立した不変 snapshot で公開する。
- 検査済み成果物の公開は、kernel 検査を通過した unit ごとに行う。
- lexical resolution と型依存の lookup は、共通の scope・visibility・依存追跡を使う。
- item の identity、内容の版、source occurrence、kernel の nominal identity を区別する。
- module instance の同一性と reflection の対応を、cache と環境の再構築を跨いで保存する。
- incremental と cold check は、同じ入力に対して同じ観測可能な結果を返す。
- CLI、LSP、MCP は、同じ意味と版管理の契約を持つ `sema` API を使う。
