# Frontend と Semantic API

## 目的

現在の `front` は source の読み込み、構文処理、名前解決、elaboration、kernel への変換を広く担っている。
これらの責務と中間表現を整理し、見通しのよいコードで、繰り返しのチェックが速い frontend にする。
完成形として、現在の source に対する semantic API と、それを使う incremental checker を提供する。
チェック済みの結果はプロセスをまたいで再利用できるようにする。

## Frontend の構造

source syntax、macro expansion、名前解決、elaboration、チェック済みの結果を、それぞれの役割が分かる表現と処理に整理する。
構文処理の段階に応じて IR や crate を分け、各段階が次の段階へ渡す情報を明確にする。
具体的な分割単位や型の形は、実装を進めながらコードの簡潔さと実行速度を基準に決める。
kernel は健全性を支える検証の責務に集中させ、semantic API、依存関係の管理、cache は frontend 側で実現する。
kernel の変更は既存の検証機能との接続に必要な範囲に抑える。

source 上の位置と、構文や宣言との対応を保持する。
`\block` や `\induction` のように期待される型に依存する構文は、その情報を使える段階で解釈する。
metavariable や constraints など elaboration 中の一時状態は、処理が終わった宣言から解放できる構造にする。
その後に必要な型、参照、依存関係、diagnostics などは semantic result として残す。

## Semantic API

semantic API は現在の source snapshot を入力とし、ファイルや宣言について parse 結果、名前解決、型、定義への参照、diagnostics、goal などを問い合わせられるようにする。
CLI と将来の editor や proof tooling は、同じ semantic result を利用する。
diagnostics と参照先には source location を含め、未解決の goal がある場合も取得できる情報を返す。

API は query ごとに必要な処理を行い、変更のない結果を再利用する。
source の変更によって影響を受ける問い合わせを正しく更新できるよう、宣言間の参照に加えて scope、import、macro など名前解決に関わる依存関係も扱う。
未保存 buffer を含む source snapshot も同じ API で扱えるようにする。

## Incremental checker と永続キャッシュ

checker は source や依存先の変更を検出し、影響を受けた範囲を再チェックする。
変更のない結果は実行中に再利用し、前回のプロセスで正常にチェックした結果も次回の実行で再利用する。
永続キャッシュの有効性は source、依存関係、言語や checker の版、関連する設定から判定する。
キャッシュを消した後も source から同じ判定結果を再構築できる。

再利用の粒度、保存する結果、永続化の形式は、実装の複雑さと実際のチェック時間を見て決める。
同一 source を続けてチェックする場合と、一部の宣言や依存先を変更する場合の両方で、再利用の効果と結果の正しさを確認する。

既存の library と tests が新しい frontend を通ってチェックでき、semantic API と incremental checker が通常の CLI checking を支える状態を完成形とする。
