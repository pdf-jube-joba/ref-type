# 大規模検査のための宣言共有と継続実行

## 目的と完了条件

名前空間の具体化で生成する状態を減らし、検査済みの宣言を共有したまま検査を進められる処理系にする。
検査量に応じて増える永続的な情報と、現在の検査に必要な常駐情報を分離し、メモリ予算に合わせて後者を管理する。
CLI の資源管理、elaboration の宣言表現、kernel の参照、保存形式までを一つの実装計画として扱う。
以下の各段階を通し、全体検査と通常の編集後検査の検証を完了する。

- `libs/topology/examples/finite_models` の `--full-check` が、依存先を含む要求範囲の全宣言を検査して受理される。
- 通常の成功経路は一つの長寿命 worker で進み、モジュール階層による分割・再起動は0回になる。
- 同一入力・同一検査文脈のソース宣言について、実行中に完了した検査を後続の依存要求へ引き継ぐ。
  特殊化の具体化、保存データの再読込、障害復旧による再実行は別に計数する。
- メモリの第一目標は現在の既定値である worker の仮想メモリ上限3072 MiB以内とし、保存・復元時のピークも含めて評価する。
  8192 MiBでの比較も行い、第一目標の達成状況と、常駐を必要とする最小の状態を報告する。
- 無変更の通常検査と `--full-check-local` は保存済みの検証結果・宣言を利用できる。
- 後述する既存テスト、規模を変えた計測、全体検査の記録を揃え、旧実行経路の整理と利用方法の更新まで完了する。

## 現状と根拠

[cohomology_examples の計測](../benchmarks/records/cohomology-examples-full-check/README.md)では、既定条件の600秒でユニークな完了モジュールが2,552個、`Check` イベントが11,321件だった。
`std` は18回検査され、対象本体には到達していない。
イベントの重複率はCPU時間の重複率とは異なり、全体の完走時間も未計測である。

個別の `cohomology_examples.Torus.Geometry.Ring.Primitive` は通常計測で92.376秒、最大RSSは6,014,584 KiBだった。
詳細計測では名前空間処理に約50.1秒、新規特殊化に約372万件が記録されている。
この値は、分割の再試行だけを改善しても単独の検査に大きな常駐量が残ることを示す。
既存の計測は環境とビルド条件が異なるため、実装時には同じ入力と環境で比較し直す。

現在の実装には次の基盤がある。

| 実装 | 現在できることと残る課題 |
| --- | --- |
| [module_manager.rs](../src/elaboration/src/elaborator/module_manager.rs) | namespace-instance cache と宣言本体の遅延化があるが、import 時に対象 namespace の宣言を列挙して予約・共有判定する。 |
| [environment.rs](../src/elaboration/src/raw/environment.rs) / [namespaces.rs](../src/elaboration/src/raw/namespaces.rs) | 引数の intern と特殊化の再利用があるが、宣言ごとに置換・共有可否・同値性の処理が残る。 |
| [kernel environment](../src/kernel/src/environment.rs) | 定義登録時の一時ノード整理と上限付きキャッシュがある。登録済みの宣言や frontend が保持する情報まで含めた常駐量の管理が必要になる。 |
| [packages/native.rs](../src/sema/src/packages/native.rs) | 同一要求内の live checker を引き継ぐが、保存・復元の主単位は checker 全体の prefix で、必要範囲と保存範囲の関係に再利用が制約される。 |
| [package_artifacts.rs](../src/elaboration/src/package_artifacts.rs) | package ごとの export/import と portable identity の基盤がある。現在の native 検査経路との接続と、保持・再配置コストを見直す。 |
| [supervisor.rs](../src/cli/src/supervisor.rs) | 時間・メモリ上限で worker を終了し、モジュール階層に沿って再試行する。子の検査でも共通依存の環境が必要になる。 |

一部の論理的定義は既に、共通の kernel 本体へ引数を渡す形で共有されている。
この共有を frontend の名前空間・宣言参照まで広げることが中心となる。

## 1. 宣言の原形とインスタンスを分離する

ソース宣言ごとに、名前、パラメータ文脈、型、本体、依存参照を持つ不変の原形を保持する。
インスタンス化された名前空間は、原形への参照、共有した引数環境、局所文脈、必要な名前の対応を持つ view とする。
名前検索は原形の索引を利用し、実際に参照されたメンバーについて特殊化を具体化する。
公開メンバーの一覧や補完も原形の索引を利用できるようにする。

宣言参照は概念上、原形の宣言IDとインスタンスIDの組で表現する。
インスタンスのキーには入力世代、元の namespace、引数、必要な局所文脈と Program 文脈を含める。
名前解決中・検査中に増える原形のメンバー表は世代を持ち、確定した原形から不変の索引を共有する。

引数の置換・intern・共有可否は、同じ引数環境を使うインスタンスで共有する。
原形の宣言ごとに異なる依存引数がある場合は、必要な引数の対応を原形に保持し、共通処理と宣言固有の処理を分ける。
置換の合成は共有DAGとして表現し、同じ組合せの繰り返し走査を記録・削減する。

exact key による再利用を入口にし、既存の conversion による同一性の判定を必要な参照へ遅延する。
conversion による共有の成否が、検査順序・具体化順序・キャッシュの生存期間に依存しないようにする。
未解決メタ変数や未確定な宣言を含む比較は、その依存状態の世代と結び付ける。

inductive、structure、Program datatype の nominal identity は、原形と意味上のインスタンスに結び付けて管理する。
相互参照する宣言群は identity を先に予約し、型・本体の具体化を段階的に進める。
現在の parameter-free namespace、閉じた引数の同値な特殊化、局所文脈を持つ参照、Program と論理項の反映の区別を既存の検査規則に沿って保つ。
kernel との境界も原形と引数の共有を利用し、具体化のためだけに frontend 全体を複製する経路を置き換える。

原形の検査と利用側の引数・適用の検査は別の仕事として管理する。
全体検査では要求範囲の全ソース宣言をスケジュールし、利用時の具体化が遅延していても、未参照の宣言にあるエラーを検出する。

## 2. 一つの検査セッションで進捗を共有する

`sema::Database` の下に、入力 snapshot、構文・名前解決索引、宣言ストア、検査キュー、完了台帳を持つセッションを置く。
ソースの読込と parse は入力世代ごとに共有し、検査対象の追加は同じセッションの要求集合を広げる操作とする。
独立した package の要求でも、共通依存は同じ宣言ストアを参照する。

スケジューラの基本単位は宣言とその検査文脈とする。
パラメータ検査や相互依存する宣言群は、既存の resolver と checker の規則に沿った単位で処理する。
module は要求範囲・名前空間・診断・進捗の単位として使い、検査済み環境の所有単位から分離する。

要求された全宣言とその依存関係を計画し、依存が検証済みになった宣言から進める。
名前解決の依存には import、macro、親スコープ、失敗した名前検索に影響するスコープの変更を含める。
精密な依存が未確定の範囲には既存の保守的な閉包を使い、参照の取りこぼしを防ぐ。

宣言の状態は未検査・検査中・検証済み・失敗として管理し、保存済みかどうかと常駐しているかどうかは別に持つ。
検査完了は未解決の義務を解消し kernel の検査を通過した時点で確定する。
保存データの読込や特殊化の再具体化は、検証済み原形の検査とは別の操作になる。

`--full-check` は開始時の検証結果の再利用範囲を空にした新しい検証世代を作る。
その世代で完了した宣言を同じ実行内で共有し、要求範囲の全完了後に結果を確定する。
通常検査と `--full-check-local` は、入力・処理系・設定・依存の一致と強制検査範囲を確認して完了台帳を初期化する。
編集時は影響する原形・インスタンス・検証結果を失効させ、LSP が保持する過去の snapshot は別世代として扱う。

## 3. 永続データと常駐データの寿命を分ける

| データ | 所有と寿命 |
| --- | --- |
| 原形、検証済みの型・本体、依存参照 | 不変の宣言ストアが所有し、保存後は必要に応じて読込・退避する。 |
| 宣言ID、インスタンスの同一性、完了台帳 | セッションで安定した参照を持ち、本文の常駐状態から独立させる。 |
| 具体化済みの型・本体、簡約・conversion・名前検索の結果 | メモリ予算付きの再構築可能なキャッシュとして扱う。 |
| メタ変数、探索中の項、暫定的な対応表 | 検査単位の作業領域で所有し、完了時に公開結果と診断に必要な部分を確定する。 |
| 診断、query 結果、LSP snapshot | 外部に公開した handle を root として追跡し、保持中の世代とデータを保護する。 |

現在の raw/kernel 共通 arena では、宣言や索引からの強参照が解放を妨げる可能性がある。
まず root と所有関係を可視化し、作業領域・キャッシュ・検証済みグラフを区別する。
不変グラフは chunk と安定した handle を使って管理し、再読込後も同じ論理的宣言を参照できるようにする。
chunk 内のローカルな番号と、chunk をまたぐ宣言・式の参照を分離する。
循環する所有関係は一体の保存単位または到達可能性の管理で扱い、参照カウントだけに依存する保持を解消する。

常駐メモリは概念上、索引、現在 pin したグラフ、検査中の作業領域、上限付きキャッシュ、保存・読込バッファに分けて把握する。
完了済み原形の本文を退避できても、入力索引や identity の量は入力規模に応じて増える。
一つの型検査・conversion が必要とする作業集合の大きさも計測し、メモリ目標の達成可能性を判断する。

メモリ圧迫時は、再構築可能なキャッシュの回収、完了データの保存と退避を行う。
検査中に参照するデータは pin し、宣言境界で解放可能な状態を増やす。
一つの重い宣言の内部にも、簡約・具体化のキャッシュ制御と中断確認を入れる。
同じデータの読込と退避が繰り返される場合は、その回数と費用を観測して pin 範囲や実行順を調整する。

型の定義的等価性を調べる際には定義本体が必要になるため、検証済みの型と本体を保存し、kernel が必要に応じて参照できる境界を作る。
キャッシュを回収しても nominal identity と参照の整合性は維持する。
構造的な intern 表や同値類の索引についても、強参照による本文の永続保持と、同一性の維持を分離する。

## 4. 保存を宣言ストアへの追加にする

検証済みの宣言群と共有式グラフを不変 object に保存し、manifest が入力・依存・coverage・参照 object を結び付ける。
package の境界は入力 identity と公開範囲に使い、object の粒度は共有グラフと保存・読込コストを基に決める。
依存先は参照として保存し、追加された宣言の保存費用を新規データと必要な索引更新に近づける。

`ArtifactCatalog`、`Relocate`、既存の export/import から、identity の検証と参照整合性の処理を利用する。
既存の package artifact は常駐環境への再配置を前提とするため、部分読込と退避に適した保存形式へ整理する。
保存時に依存全体の到達可能性走査、catalog の複製、共有式の再符号化が繰り返される箇所を計測して置き換える。
圧縮・展開は上限付きバッファで行い、保存のための一時メモリにも予算を設ける。

中断用の checkpoint は、確定済み object と完了台帳、再開に必要なキューを参照する。
object を保存した後に manifest を原子的に公開し、中断時も確認できた完了範囲から再開できるようにする。
実行中の検証完了、永続化完了、要求全体の成功をそれぞれ区別する。
復旧時は処理系 fingerprint、入力、依存、object の完全性を照合し、失効した範囲を再検査する。
既存の store lock、lease、GC の参照追跡をこの単位に接続する。

## 5. supervisor を監視と復旧へ整理する

CLI は一つの worker にセッション全体を任せ、supervisor が進捗、利用者の中断、資源上限、異常終了を監視する。
メモリの軟上限で worker に回収・保存を要求し、OS の硬い上限までに保存用の余裕を確保する。
既存のメモリ指定が制限する仮想メモリと、RSS・allocator の保持量を区別して扱う。
elapsed time、進捗の停滞、利用者が指定した総時間制限も別に管理する。

異常終了や硬い上限による中断からは、最後に公開した完了台帳と object を使って同じ要求を再開する。
通常の実行を新方式へ移行した後、階層分割を行う `Batch::split`、分割 layout、prefix の広狭による再試行を整理する。
CLI の進捗と report は、検査・具体化・読込・保存・回収・復旧を区別して表示する。

## 実装順序

1. **比較条件と保持量を確定する。**
   現在の入力とバイナリを固定し、個別検査と全体検査の基準値を採る。
   宣言原形、予約済み特殊化、実際に具体化した特殊化、式ノード、引数・置換表、キャッシュ、保存バッファの件数と保持量を観測できるようにする。
   同じソース宣言の再検査と、異なる特殊化の処理を区別するカウンタを追加する。
2. **名前空間を原形と view に変える。**
   名前検索から実際に参照する宣言を具体化し、引数環境と同一性をインスタンス単位で管理する。
   kernel、Program、反映、診断まで参照を接続し、Torus で予約・具体化件数と常駐量を比較する。
3. **宣言ストアと常駐量の管理を導入する。**
   作業領域と不変グラフを分け、安定した参照、chunk 保存、部分読込、pin と退避を実装する。
   保存・読込経路も含むメモリ予算を導入し、現在の prefix 全体を必要とする箇所を置き換える。
4. **セッション全体の検査キューと完了台帳を接続する。**
   package 間で共通依存を共有し、要求の追加・部分選択・全体検査・編集後の失効を同じ仕組みで処理する。
   検査済みの本文を再読込して後続を検査できることと、未参照宣言も全体検査に含むことを確認する。
5. **継続実行と復旧へ移行する。**
   長寿命 worker と supervisor を接続し、新方式で全体検査を完走させる。
   強制中断後の再開、保存失敗時の診断、通常検査の再利用を確認して旧経路を整理する。
6. **比較計測と既存検証を完了する。**
   以下の計測を実施し、達成した資源条件、全件の検査結果、残る最大の費用を記録する。
   `src/sema/README.md`、`src/artifact/README.md`、`src/kernel/README.md`、`src/USAGE.md` を最終実装に合わせて更新する。

## 検証と計測

計測用の入力・スクリプト・要約は `benchmarks/` に置く。
大きなログ、バイナリ、cache は `benchmarks/runs/` に置き、記録にはコマンド、入力とバイナリの digest、資源条件、結果を残す。
ビルド・テストと計測を時間的に分け、詳細プロファイルと通常の時間計測を別々に採る。
短い対象は3回の中央値、長い全体検査はまず1回の完走を必須とし、回数を明記する。

### 既存の検証

`cargo test --workspace --locked`、`cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets --locked -- -D warnings` を実行する。
CLI をビルドし、`python3 tests/tests.py` で既存の受理・拒否ケースを確認する。
変更箇所では特に module 引数、局所文脈、nominal identity、Program の反映、metavariable、保存・復元と失効の既存ケースを確認する。
ライブラリの計測入力と処理系の検証用 fixture は独立して扱う。

### 規模に対する増え方

ベンチマーク生成器で次の軸を独立に変化させる。

| 入力 | 確認する性質 |
| --- | --- |
| 既存の package 依存チェーン | 原形の検査回数と保存量が追加宣言に応じて増え、完了済み prefix の処理が累積しないこと。 |
| 共通依存を持つ多数の利用側 | 共通依存の原形の検査回数が利用側の数から独立すること。 |
| 大きな namespace から少数の宣言を参照 | 原形の読込・検査費用と、インスタンスごとの具体化費用を分け、後者が使用メンバーとその依存に応じて増えること。 |
| 同一引数・異なる引数・局所文脈を持つ import | 共有できる範囲と意味上異なるインスタンスを区別できること。 |
| 多数の独立した宣言群と、小さい常駐予算 | 完了本文の退避が進み、再読込による検査のやり直しと過剰なI/Oが生じないこと。 |

サイズを倍増させたときの検査時間、具体化件数、常駐量、保存量の推移を記録する。
型検査や conversion 自体の難しさと、管理処理の増え方は区別して評価する。

### 実ライブラリ

- Graph、Mayer–Vietoris の Chains、Torus の Primitive を既存記録と同じ選択範囲で測り、namespace と kernel の費用を分ける。
- `cohomology_examples` は依存を含む `--full-check` を完走させ、要求範囲の coverage と受理結果を照合する。
- `singular_cohomology` と `manifolds` でも全体検査を行い、異なる依存構造での効果を確認する。
- 通常検査、`--full-check-local`、依存の編集、checkpoint 公開後の中断・再開を測り、再利用と失効が成立することを確認する。

最終記録には wall time、CPU時間、最大RSS、最大仮想メモリ、worker 数、原形の重複検査数、具体化件数、保存・読込バイト数、回収量、再開で失った作業量を含める。
旧方式が時間上限で終わる場合は打切り値として扱い、新方式の完走時間との倍率は算出可能な範囲に限る。
メモリ目標が未達の場合は、残った索引・pin された本文・一宣言の作業領域・保存バッファのどれが支配的かを示し、この計画内で必要な保持方式の改善を続ける。
