# singular_cohomology の検査時間と展開コスト

`libs/` を変更せず、処理系と保存・復元の方法を変更した。
全2361モジュールの `--full-check` は461.248秒で完了し、検証結果の永続キャッシュ再利用は false だった。
提示された1298.677秒に対して約2.8倍の速さになったが、100秒には達していない。
提示された時間は利用者側の計測なので、同一条件の繰り返し比較ではない。

全体検査は WSL2 Linux x86_64、`cargo build -p cli --locked` の dev profile（opt-level 2）、worker ごとの仮想メモリ上限3072 MiB、分割まで180秒で計測した。
各全体検査は空の成果物キャッシュから開始し、実行内で生成した依存環境を共有する。
singular_cohomology は、従来の4つの分割ヒントだけを初期状態にした。
検査中に Relative.Maps と Relative.Equivalence で広い保存環境の再利用が上限に達し、必要範囲に絞った再試行で完了した。
その選択を次回のヒントに保存する。
manifolds は分割ヒントも空の状態から計測した。
With の個別計測は両方ともキャッシュを無効にし、`REF_TYPE_PROFILE_COSTS=1` と `REF_TYPE_PROFILE_PHASES=1` を指定した。
時間は各1回の観測で、詳細計測には追加のコストがある。

## 行数と内部の処理量

依存を含む `.ref` の行数は singular_cohomology が83461行、manifolds が57717行で、差は約1.45倍である。
入口 package 自身はそれぞれ8478行、2452行で、読み込む package は19個と14個である。
異なるプログラムの2点だけから、行数 \(N\) に対する計算量の次数は決められない。

With の変更前の計測では、namespace の処理に排他的時間で約71.0秒、kernel に約10.8秒かかっていた。
module 引数の比較は35083745回で、26110480回が未解決の比較だった。
変更後は比較が1339714回、未解決の比較が341994回になり、namespace の排他的時間は約9.24秒、kernel は約4.48秒になった。
行数よりも、引数別に生成する namespace・宣言、引き継ぐ import の数、それらの比較と再構築が大きく効いていた。
With の最大RSSは変更前2111028 KiBから増えており、時間とメモリの両方が同じ割合で改善したわけではない。

元の宣言と同値と確認できた引数を索引にし、過去の全候補を探す比較を減らした。
局所文脈を持たない論理的な定義は本文を一度 kernel に登録し、具体化した参照から引数を渡す。
環境は resolver・raw/kernel・完了ステップを一緒に復元し、重なる環境を再配置して統合する処理を検査経路から外した。
名前解決も検査対象の依存閉包に絞り、同じ環境で処理できる利用側と依存先をまとめる。
保存時は宣言の行をストリームで符号化し、復元時は namespace の不変な名前表とラベルの共有を戻す。

引数別の frontend 宣言と namespace の展開は残っている。
また、復元した名前解決範囲に後続の宣言が含まれていない場合は、その選択の環境を再構築する。
これらが100秒へ向けて残る大きな処理である。
固定16宣言の package を連結した別の [workload](scaling.json) は、深さ8・16・32・64で0.183・0.343・0.726・1.551秒だった。
